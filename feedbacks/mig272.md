# mig272: the rust edition's tests onto std2 (0.27.2)

## Verdict

The `// ENV: VOLE_STD2=0` opt-out is gone from every test case: 383 in
tests/run, 5 in tests/borrowck-try and one merged in later. 265 ran on
std2 unchanged, once places.verify's I7 fix (clos272) was merged. 64 were
rewritten into Rust's spellings on std2 (28 of them passing only once a
user Drop ran on std2). 54 are `// XFAIL: <gap> (<stream>)`, each naming
the compiler or std2 gap that stops it. Two
scripts still set VOLE_STD2=0 because of gaps: tests/guide/run.sh (the
edition page's first example) and tests/refactor/testrust.t (std2 has no
contract_check and no Vec::iter). compile_cost's rust row on std2 waits
for a decision: checking a std2 program costs 8x what 0.27.1 costs on MVS
std.

## What to fix, with a tag

- [hook] Fixed here: check-after-edit.py (and turn-end.py, which goes
  through its verify()) checked a test case without its `// FLAGS:
  --edition rust` and `// ENV: VOLE_STD2`. A rust case was then fixed
  into MVS's spellings: `&mut i64` became `inout i64` and `let mut`
  became `var`. The hooks that run are the main checkout's, so until
  this merges, an agent editing a rust case there still gets those
  fixes.
- [tool] `volec check` of any std2 program inside the tree reports
  about 10 errors in std2's uninstantiated bodies, which a build does
  not report. Every check hook result on a rust case is 50 errors of
  noise, which hides the case's own errors. Known (front272 Z4,
  clos272).
- [tool] The check hook's help for a std2 program names MVS paths: "add
  `use std::iter::Range;` or `use std::window::objc::Range;`", and "'env'
  is std's module std::env". Its did-you-means come from MVS's std, not
  the edition's.
- [gap] Larger than expected, now fixed (clos272): on std2 a user `impl
  Drop` never ran (no drop elaboration), and the borrowck codes that need
  Drop (move_from_drop, dropped_borrowed) were not raised. This blocked
  28 cases until the fix was merged.
- [gap] `Vec<&str>` and `Vec<&[T]>` instantiate as `Vec<str>` and
  `Vec<[T]>`: the reference is lost in a type argument of unsized
  referent (Vec<&i64> is fine).
- [process] The XFAIL'd cases are rewritten only as far as their first
  gap. When a gap closes, a case may show the next one (some still use
  MVS's `sort_by(slice, f)` or `Ord::cmp -> i64` behind a Vec::iter
  XFAIL: rust_t_iter_sources_named_fns, rust_t_iter_for_sources).
